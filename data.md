# ERA5 Data Request, Download, and Preprocessing Instructions

## 1. Data Source

This project uses ERA5 reanalysis data provided by the Copernicus Climate Data Store (CDS). The data are freely available, but users need to register for a CDS account, log in, and accept the license terms of the corresponding datasets.

- [Copernicus Climate Data Store](https://cds.climate.copernicus.eu/)
- [ERA5 hourly data on single levels](https://cds.climate.copernicus.eu/datasets/reanalysis-era5-single-levels?tab=download)
- [ERA5-Land hourly data](https://cds.climate.copernicus.eu/datasets/reanalysis-era5-land?tab=download)
- [CDS API User Guide](https://cds.climate.copernicus.eu/how-to-api)

This project recommends using **ERA5 hourly data on single levels**. ERA5-Land is used only as a supplement when higher-resolution land-surface variables are needed, and it cannot be directly mixed with ERA5 Single Levels data without preprocessing.

## 2. Request and Download Workflow

1. Go to the [CDS website](https://cds.climate.copernicus.eu/), register, and log in.
2. Open the page for the required dataset, read and accept the license terms.
3. On the dataset **Download** page, select variables, years, months, days, times, spatial extent, and file format.
4. Small amounts of data can be submitted and downloaded through the web interface; for batch downloads, follow the API request generated by the page and the [official CDS API guide](https://cds.climate.copernicus.eu/how-to-api).
5. After downloading, organize different variables into separate NetCDF files and complete unit, time, and grid checks as required below.

CDS pages are adjusted as the platform is updated, so this document does not repeat specific buttons and API parameters. When downloading, follow the latest official guidance displayed on the dataset page.

## 3. Variables Required by This Project

The public code reads the following files by default from the `data/` folder under the project root:

| File name | CDS variable | Raw form and main processing |
|---|---|---|
| `tp_hourly.nc` | Total precipitation | In ERA5 Single Levels, this is precipitation accumulated over the previous hour, usually expressed in m; no temporal differencing is needed. The code multiplies by 1000 according to the configuration to convert to mm |
| `u10.nc` | 10m u-component of wind | Instantaneous quantity, usually in m s⁻¹ |
| `v10.nc` | 10m v-component of wind | Instantaneous quantity, usually in m s⁻¹ |
| `d2m.nc` | 2m dewpoint temperature | Instantaneous quantity, usually in K |
| `tcwv.nc` | Total column water vapour | Instantaneous quantity, in kg m⁻²; numerically equivalent to mm water depth |
| `evaporation.nc` | Evaporation | Accumulated over the previous hour, usually in m; ERA5 uses a downward-positive flux convention, so evaporation is usually negative. The code performs unit and sign conversion |
| `vimd.nc` | Vertical integral of divergence of moisture flux | Raw unit is usually kg m⁻² s⁻¹; positive values indicate moisture divergence. You can retain the raw flux rate and integrate in code, or pre-convert it to hourly water amount |

This project uses April–September data from 2020–2023 by default, where 2020–2021 are used for training, 2022 for validation, and 2023 for testing. If other years or months are used, the data split configuration in the code should be modified accordingly.

The recommended directory structure is as follows:

```text
project_root/
├── data/
│   ├── tp_hourly.nc
│   ├── u10.nc
│   ├── v10.nc
│   ├── d2m.nc
│   ├── evaporation.nc
│   ├── tcwv.nc
│   └── vimd.nc
├── geoconvlstm_baseline_8h.py
├── geoconvlstm_physics_finetune_8h.py
└── visualize_water_budget_example.py
```

ERA5 files are usually large, so it is not recommended to commit raw data and model outputs directly to GitHub. You can exclude `data/` and `outputs/` in `.gitignore`.

## 4. Key Differences Between ERA5 and ERA5-Land Precipitation Data

| Item | ERA5 hourly data on single levels | ERA5-Land hourly data |
|---|---|---|
| Grid | 0.25° × 0.25° | 0.1° × 0.1°, native resolution approximately 9 km |
| Temporal frequency | Hourly | Hourly |
| Meaning of hourly TP | Accumulation over the hour ending at the current valid time | Accumulation from the start of the daily 00 UTC short-range forecast to the current forecast step |
| Method to obtain hourly precipitation | Multiply by 1000 to convert m to mm; can be used directly | Difference adjacent accumulation steps within the same forecast cycle |
| Compatibility with this project's code | Recommended; can be preprocessed directly according to the file structure in this document | Must first handle the accumulation convention and regrid to a unified grid |

### ERA5 Single Levels

In CDS, the hourly `total_precipitation` in ERA5 Single Levels is a one-hour accumulation. For example, a value labeled 08:00 UTC represents precipitation during the hour ending at 08:00 UTC. It is not an instantaneous precipitation rate, but it is already in hourly increment form, so only unit conversion is needed and no further temporal differencing is required:

```text
tp_hourly_mm = tp_era5_m × 1000
```

### ERA5-Land

Precipitation and other accumulated variables in ERA5-Land use a different convention: a short-range forecast starts at 00 UTC, and forecast steps 01–24 respectively store the total accumulated from the forecast start to that step. Hourly increments should be computed within the same forecast cycle:

```text
step 1:      tp_hourly = accumulation(step 1)
step 2—24:   tp_hourly = accumulation(step n) - accumulation(step n - 1)
```

Do not apply a single global difference directly to the full ERA5-Land time series, because the daily forecast cycle resets. In particular, handle the cycle boundaries around 00 UTC/01 UTC separately; otherwise large negative precipitation values may occur.

This document only discusses hourly products. Monthly mean products have different accumulation periods and unit definitions, so the processing methods above cannot be applied directly.

## 5. Overview of Data Preprocessing

After downloading, it is recommended to perform the following steps in order:

1. **Check metadata**: Confirm variable names, units, time coordinates, latitude/longitude coordinates, dataset name, and accumulation convention. Do not judge only by file name.
2. **Filter spatiotemporal range**: Subset the data by study area, year, and month. All variables must use the same spatial and temporal ranges.
3. **Unify coordinate names**: Rename `valid_time` or other time dimension names to `time`, unify latitude and longitude to `lat` and `lon`, and remove duplicate timestamps.
4. **Confirm where unit conversion is handled**: The public code reads ERA5 TP and evaporation in m by default and converts them to mm at runtime, so do not convert them offline and still keep `m_per_hour` or `hourly_amount_m` configuration. Wind speed can remain in m s⁻¹, dewpoint temperature can remain in K, and TCWV in kg m⁻² is numerically equivalent to mm water depth.
5. **Handle accumulations and flux rates**: Hourly TP in ERA5 Single Levels is no longer differenced; ERA5-Land accumulated variables are differenced by forecast cycle; if raw VIMD is in kg m⁻² s⁻¹, multiply by the actual time interval in seconds either during preprocessing or in the code, choosing only one of the two.
6. **Unify grids**: Data with different resolutions or inconsistent coordinates must be regridded first. ERA5-Land 0.1° data cannot be directly used cell-by-cell with ERA5 0.25° data.
7. **Check temporal continuity**: Before calculating differences between adjacent times, confirm that the interval is indeed 1 h. Long gaps caused by month boundaries, season boundaries, or missing data must be masked.
8. **Quality check**: Check missing values, anomalous negative precipitation, duplicate times, latitude/longitude orientation, and array shapes for each variable. If files contain additional dimensions such as `expver`, first merge valid values or remove singleton dimensions.

After temporal filtering, coordinate unification, and necessary accumulation processing, the data can be saved as the NetCDF files listed in the table above. The model code performs unit conversions for TP, evaporation, and VIMD according to the configuration, and performs standardization during training. Therefore, it is not necessary to pre-apply z-score standardization to all input variables.

## 6. Water Vapor Budget Variable Processing

The column water vapor budget used in the Physics version is:

```text
P_budget = E_up - ΔTCWV - VIMD_interval
```

where:

```text
E_up = -evaporation × 1000
ΔTCWV = TCWV(t) - TCWV(t - 1)
VIMD_interval = VIMD_rate × Δt
```

- `E_up` uses the upward-positive convention; when raw ERA5 evaporation is negative, taking the negative sign gives positive evaporation water amount.
- `ΔTCWV` is only allowed to be calculated between consecutive adjacent times.
- When raw VIMD is in kg m⁻² s⁻¹, 1 kg m⁻² is numerically equivalent to 1 mm water depth, so continuous hourly data are usually multiplied by 3600 s.
- If `vimd.nc` has already been converted to hourly water amount during preprocessing, set `VIMD_TIME_INTEGRATION_MODE` to `"none"` in the code; if the raw flux rate is retained, set it to `"multiply_dt"`. Choose only one of the two to avoid multiplying by 3600 twice.

All water vapor budget terms should ultimately be unified as mm water amount per time interval before grid-cell calculations and comparisons can be performed.

## 8. Additional Notes

For other variables contained in the ERA5 dataset, you can add them to the input channels as needed. You do not necessarily have to use the variables selected in the paper; our variables are a small set selected through correlation analysis to preserve the information provided by the features while reducing computational cost.

If the amount of data requested at one time is too large, you may need to wait in a queue to obtain the data. The time range of the selected data can affect the queue speed for data requests, while the spatial extent only affects the download speed. Therefore, when sufficient computing resources are available, it is recommended to request different data in separate batches.

If you are proficient in handling grid-format data files, you may choose that format, but in general NetCDF format (`.nc`) is recommended.
